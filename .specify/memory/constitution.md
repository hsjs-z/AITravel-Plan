# 旅行规划平台 Constitution

## Core Principles（核心原则）

本节十项原则均为**不可协商（NON-NEGOTIABLE）**：任何一项被违反即构成合规失败，
必须修复或经治理流程显式豁免后方可合并。以下「必须 / 禁止」均为强制要求，
而非建议。

### I. 微服务工程结构（Monorepo + 边界隔离）

工程必须保持单仓库 Maven 聚合结构：根 pom 统一管理依赖与版本，`common` 为公共模块，
每个业务模块各自是一个可独立部署的微服务。

- 业务模块之间**禁止**互相依赖代码；跨模块复用只能下沉到 `common`。
- 服务间通信只能通过 OpenFeign（同步）或 Kafka 事件（异步）；**禁止**跨模块直接访问
  对方的数据库、表或内部实现。
- 新增模块必须遵循既有聚合结构并在根 pom 中注册，不得旁路到独立仓库或独立构建体系。

理由：保证服务可独立部署与演进，防止架构退化为「分布式单体」。

### II. 技术栈锁定（Stack Lock）

技术栈为：JDK 17 + Spring Boot 3 + Spring Cloud Alibaba（Nacos 注册与配置、
Spring Cloud Gateway、Sentinel 限流、Seata 事务、OpenFeign）+ Spring AI + DeepSeek
+ Kafka + Redis + MySQL。前端：Vue 3 + Vite。

- **禁止**引入功能等价的替代品（如以 Eureka/Zuul/Resilience4j 替代 Nacos/Gateway/
  Sentinel，或以 RabbitMQ 替代 Kafka），除非先按治理流程修订本宪章。
- 依赖升级与替换必须走宪章修订并评估对既有原则的影响。
- 版本号以根 pom 的 dependencyManagement 为唯一事实来源，模块内不得各自锁定冲突版本。

### III. 核心链路优先（AI 规划 → 行程 → 预订/订单 → 支付）

主线链路「AI 规划服务 → 行程服务 → 预订/订单服务 → 支付服务」必须端到端跑通。

- 任何迭代都不得使该主线的端到端可用性回退；主线必须有可执行的端到端验证路径。
- 商家结算、后台管理属于**可延后模块**：其未完成不得阻塞主线交付；
  但其接口与数据边界不得破坏主线依赖关系。
- 需求排期冲突时，主线优先于可延后模块。

### IV. 分布式一致性与可靠事件

- 跨服务写操作（例如行程中包含的「酒店 + 门票」联合预订）**必须**使用 Saga 编排，
  并为每个正向操作定义明确的失败补偿动作；补偿必须幂等且可重放。
- 事件发送**必须**使用 Outbox 模式：业务数据与待发事件在同一本地事务内落库，
  再由投递器异步发送，保证**不丢**；消费端必须基于幂等键去重，保证**不重**。
- 跨服务一致性以 Saga + 补偿为默认方案；2PC 式强一致**禁止**作为默认实现。
  Seata 仅用于已明确声明并记录的场景（例如单服务内的本地事务编排）。

### V. 支付抽象与幂等

- 支付**必须**通过 `PaymentGateway` 接口抽象：开发期使用 Mock 实现，并预留真实微信支付
  的实现位；新增实现不得要求修改调用方代码。
- 支付与退款**必须**基于幂等键（idempotency key）实现幂等：相同幂等键的重复请求
  必须返回相同结果，**禁止**重复扣款或重复退款。
- 支付回调**必须**做对账：校验签名、金额与订单状态，并与本地记录比对；
  回调通知必须可重试且最终一致。
- 所有支付/退款状态变更必须落库留痕并可审计。

### VI. AI 规划异步化与任务状态机

- 调用 DeepSeek 的 AI 规划**必须**异步执行；**禁止**任何形式的同步阻塞请求等待模型返回。
- 必须实现任务状态机：`PENDING → RUNNING → SUCCEEDED / FAILED`，
  并提供任务状态查询与失败重试入口。
- 对外接口只返回任务标识；结果通过查询或事件产出，超时与重试策略必须显式定义。

### VII. 并发安全与库存原子扣减

- 热门酒店/门票等资源的库存扣减**必须**原子化：使用 Redis 分布式锁或原子操作
  （Lua 脚本 / 原子命令）完成；数据库乐观锁或唯一约束作为兜底。
- **禁止**任何跨请求生效的「查询 → 判断 → 修改」非原子实现。
- 库存扣减正确性必须有并发测试或压测证据支撑，不得以「本地单线程验证通过」作为交付依据。

### VIII. 可观测性

- 所有服务**必须**接入 OpenTelemetry，且 traceId 必须跨服务透传：
  链路贯穿 AI 规划 → 订单 → 支付；异步链路（Kafka、异步任务）同样必须透传上下文。
- 关键接口**必须**产出量化指标（QPS、P99 延迟），且可从监控或日志中查询验证。
- 日志必须结构化，**禁止**输出 API Key、口令、支付要素等敏感数据。

### IX. 代码标准与分层

- 每个模块内部必须遵循 Controller / Service / Repository 分层：
  业务逻辑不得写在 Controller，Repository 不得承载业务规则，禁止跨层直连。
- 对外接口（REST/Feign DTO、事件 Schema）**必须**有文档（OpenAPI 或等价的接口说明），
  接口变更必须同步更新文档。
- API Key、数据库口令等敏感配置**只允许**通过环境变量注入；
  **禁止**硬编码或提交到仓库。非敏感配置统一由 Nacos 管理。

### X. 质量底线（测试即完成定义）

- 核心业务逻辑**必须**有单元测试覆盖：订单状态机、Saga 编排与补偿、幂等键处理、
  库存扣减。
- 未经通过的测试不得标记为完成；测试失败即视为未完成，不得以「后续补测」结项。
- 主线链路必须具备集成或端到端测试，用于验证 III 所述的端到端可用性。

## Architecture & Runtime Constraints（架构与运行约束）

**模块拓扑（不得偏离）**

- 根 pom：聚合所有模块，集中声明依赖版本（BOM / dependencyManagement）。
- `common`：公共模块，仅承载可被所有服务复用的通用能力（DTO、异常、工具、
  可观测性封装、Outbox / Saga 基础抽象等）。
- 业务模块：AI 规划服务、行程服务、预订/订单服务、支付服务，以及可延后的
  商家结算、后台管理等模块。

**通信与入口**

- 对外统一经 Spring Cloud Gateway 进入；服务注册与配置由 Nacos 承担。
- 热点接口必须配置 Sentinel 限流规则，规则随配置管理，不得只存在于代码注释中。
- 跨服务同步调用使用 OpenFeign（需带超时与降级策略），异步协作使用 Kafka 事件。

**本地运行与依赖**

- 开发环境需提供 MySQL、Redis、Kafka、Nacos 的可复现启动方式（如容器编排文件），
  使主线链路可在本地端到端验证。
- 开发期支付使用 Mock 实现，但 `PaymentGateway` 接口契约必须与真实实现保持一致。

**可延后模块的约束**

- 可延后模块可暂缓实现，但其与主线的接口边界、事件契约必须先固化并文档化，
  避免后续返工破坏主线。

## Development Workflow & Quality Gates（开发工作流与质量门禁）

- 需求必须走规范驱动流程：先规格（specify）→ 再设计（plan）→ 再拆任务（tasks）→
  最后实现（implement）。实现开始前必须完成 plan 中的 Constitution Check，
  逐项确认原则 I–X 无冲突。
- 每个 PR / 评审必须声明对本宪章的合规性；存在违规且未获豁免的变更不得合并。
- 偏离宪章的做法必须记录为 ADR 或例外条目，包含动机、影响范围与失效条件。
- 跨模块新增依赖、对外接口变更、事件 Schema 变更必须同步文档，并说明对主线的影响。
- 「完成」的定义包含：实现 + 通过测试 + 文档更新 + 合规声明。

## Governance（治理）

- 本宪章优先于其他一切实践与约定；出现冲突时以本宪章为准。
- 修订流程：提出修订（说明动机与影响）→ 影响评估 → 更新本文件并记录版本与日期 →
  检查依赖模板（plan/spec/tasks）是否需要同步。
- 版本策略（语义化版本）：
  - **MAJOR**：不兼容的治理变更，或原则的移除 / 重新定义。
  - **MINOR**：新增原则或对既有原则的实质性扩展。
  - **PATCH**：措辞澄清、错别字修正等非语义变更。
- 合规审查：所有 PR / 评审必须验证合规性；任何复杂度与偏离都必须论证；
  运行时开发指导以本文件为唯一来源。
- 例外与豁免必须显式记录（ADR 或例外条目），并明确有效期；到期未收敛即视为违规。
